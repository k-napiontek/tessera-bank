| 2026-08-18 | A PostgreSQL trigger function must address its tables through **`TG_TABLE_SCHEMA`**, never by an unqualified name. A function body resolves unqualified names against the *caller's* `search_path`, not the schema it was created in, so the balanced-entry trigger worked during migration and failed the moment it was called from a connection with a different `search_path`. |
| 2026-08-19 | **The use cases live in `ledger-core`, not in the web module.** Each holds the sequencing no single aggregate can - take the transaction, lock the accounts in a safe order, ask the domain to decide, write the result - and that sequencing is the part of a ledger most easily got wrong. Here it is driven by in-memory fakes in milliseconds; in a controller it would need a database and an HTTP request to exercise at all. They reach infrastructure through a new `UnitOfWork` port, which expresses the transaction boundary. **The lock ordering stays in the adapter**: the port asks for a *set* of accounts, not a sequence, precisely so that no caller can choose an order, and WP-07's `AccountLocks.lockInOrder` remains the only thing that decides one. |
| 2026-08-19 | **An account reference is supplied by the caller, not allocated by the ledger.** `customer-master` owns onboarding and the numbering series, and the ledger holds no customer identity. That is what makes `POST /accounts` idempotent without an `Idempotency-Key`: a retry names the same reference, and opening one that already exists is a `409` rather than a second account. Idempotency as a property of the request, rather than of a header. |
| 2026-08-19 | **A replay answers `200`, whatever the original returned, and only a 2xx is ever recorded.** `201 Created` asserts that something was created *now*, and repeating it for a request that created nothing this time would be false - so the contract declares `200` on all five money-moving operations and a replay uses it. Recording a failure would be worse than useless: a stored `422` would answer a client's corrected retry forever, so a non-2xx rolls the transaction back and releases the claim along with anything the request wrote. |
| 2026-08-19 | **The idempotency claim is `INSERT ... ON CONFLICT DO UPDATE`, never `DO NOTHING` and never a read followed by a write.** `DO NOTHING` does not wait for a conflicting row another transaction has inserted but not committed - it skips, and the following `SELECT` cannot see the uncommitted row either, so both retries conclude the key is theirs. Proved by mutation: with `DO NOTHING`, eight threads retrying one request executed it eight times. The no-op assignment in `DO UPDATE` exists only to take the row lock. |
| 2026-08-19 | **The request fingerprint is over canonical JSON, not raw bytes.** Object keys sorted recursively, whitespace ignored, array order preserved - because in JSON an array's order is meaning rather than presentation. A client that retries by re-serialising its request means nothing by the new field order, and digesting the bytes would refuse a legitimate retry with a `409`. The digest also covers the method and the resolved path, so one key on `/holds/A/release` and `/holds/B/release` is two operations rather than one. |
| 2026-08-19 | **The contract test validates with a JSON Schema 2020-12 implementation, not an OpenAPI one.** OpenAPI 3.1 schemas *are* JSON Schema 2020-12 - that is the headline change of 3.1 - and `ledger-core.yaml` uses it: `type: [string, 'null']` cannot be expressed in 3.0. The OpenAPI validators in the Java ecosystem still read 3.1 by converting it down to 3.0, losing exactly those constructs. Validating against a downgraded copy of the contract would be a test that agrees with itself. |
| 2026-08-19 | **`openedDate`, `lastMovementDate`, an entry's posting instant and its reversal link are read-model fields.** All four are required by the REST contract and none guards an invariant, so they are read from the rows the repositories already write rather than added to `Account` or `JournalEntry`. Adding a derived field to an aggregate to satisfy a response schema is the persistence-shaped back door F-21 records being refused for `Hold`. `Transfer.status` is derived the same way: `ACCEPTED` and `REJECTED` never reach the database, because a rejected transfer is a Problem document and not a row. |
| 2026-08-19 | **`ledger-api`'s test container is started in a static initialiser, not by `@Testcontainers`.** That extension stops a `@Container` when the class declaring it finishes, while Spring caches its context - and the Hikari pool inside it - across every test class in the module. The second class then holds connections to a container that no longer exists and fails with "Failed to obtain JDBC Connection", for a reason unrelated to what it was testing. Ryuk removes the container on JVM exit, the same arrangement `PostgresSupport` uses in `ledger-persistence`. |
| 2026-08-19 | **The audit trail's two mechanisms do different jobs and are stated separately.** A row trigger stops the application editing a row; the hash chain catches whoever gets past it - a superuser, a DBA with DDL rights, a restored backup. Nothing can prevent the second, and a control that claims to prevent what it can only detect is worse than one that admits the difference. The statement-level `TRUNCATE` trigger beside the row-level one is not decoration: `TRUNCATE` fires no row trigger, so without it one statement empties the trail while the control never runs. See ADR 0005. |
| 2026-08-19 | **The tamper-evidence control is the encoding, not the digest.** Every implementation of SHA-256 agrees; what decides whether a chain is tamper-evident is whether two different entries can hash to the same value. `AuditEntry`'s canonical form is length-prefixed because a concatenation lets `{"a": "bc"}` and `{"ab": "c"}` collide, and an auditor could then be shown either row with the chain verifying for both. An absent value encodes differently from an empty one for the same reason. |
| 2026-08-19 | **What is hashed is normalised first.** `timestamptz` keeps microseconds while `Instant` carries nanoseconds, and a `uuid` column returns lowercase whatever case it was given. Hash before normalising and verification reports tampering on rows nobody touched - and a control that cries wolf gets switched off, which is worse than not having it. |
| 2026-08-19 | **The relay publishes, then marks. Never the reverse.** Marking first turns every failed publish into a permanently lost event, because the row already claims to be done. Publishing first means the relay can die between the broker's acknowledgement and the mark, and the next pass republishes - at-least-once, which the AsyncAPI document has declared since WP-02. Proved by mutation: swapping the two lines fails three tests in `OutboxRelayTest`. |
| 2026-08-19 | **A relay batch stops at its first failure rather than skipping the stuck row.** Events for one transfer must reach the broker in the order they were written; publishing past a failure can deliver a reversal before the transfer it reverses. One stuck row therefore blocks the queue, which is the usual shape of an outbox incident and is what the runbook opens with. |
| 2026-08-19 | **The audit row omits the remittance reference; the event carries it.** The two exclusions look inconsistent and are not. It is the one field a paying customer controls, classified restricted-if-misused - and an audit row is an internal record retained for years, while the event is how that reference reaches the ESB, which encodes it into a `MOVEREC` for the mainframe to print. The exclusions differ because the consumers do. A reversal's `reason` **is** recorded, because the contract calls it operator-supplied and forbids personal data in it. |
| 2026-08-19 | **A correlation id is now generated when the caller sends none.** WP-08 recorded the opposite - "never invented here, because an id minted per tier correlates nothing" - and that reasoning held for echoing and not for absence: a request arriving without one was simply untraceable. A non-UUID is replaced rather than propagated, because whatever arrives reaches log lines and a Problem document, and honouring arbitrary text would let a caller choose this service's log contents. |
| 2026-08-19 | **The database is in the readiness probe and deliberately not in liveness.** Spring's default readiness group is `readinessState` alone, which reports ready as soon as the context has started - so a ledger that cannot reach PostgreSQL is declared ready and sent traffic it can only reject. Rejections are counted but not timed. |
